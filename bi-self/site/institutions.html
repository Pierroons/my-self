SelfRecover — pour les institutions

Services régaliens, opérateurs publics, grandes entreprises : ce que vous pouvez faire avec un protocole open-source que personne ne contrôle, et que vous pouvez auditer ligne à ligne.

Positionnement

SelfRecover est un protocole publié en avril 2026 sous licence AGPL-3.0-or-later, avant la fuite ANTS du 15 avril 2026 (dont les chiffres sont rappelés sur la vitrine). Cette page n'est ni un argumentaire commercial ni une réponse à appel d'offres : c'est un point de référence factuel pour vos équipes technique, juridique et achats si vous envisagez de tester, intégrer ou auditer le protocole.

Le démarchage initial est non commercial. La priorité est qu'un standard ouvert utile à plusieurs services publics existe et fonctionne. Toute prestation associée (audit complémentaire, accompagnement intégration, formation) peut faire l'objet d'un échange ultérieur si l'organisation le souhaite — pas de devis spontané, pas de NDA.

FAQ — questions habituelles d'un cabinet ou d'une DSI

Quelle licence et quelles obligations pour notre service ?
AGPL-3.0-or-later. Concrètement : libre intégration, libre modification, libre distribution. Toute version déployée publiquement (y compris derrière un service web public) doit publier ses modifications sous la même licence. Pas de capture SaaS possible. C'est exactement le même mécanisme que Nextcloud, Mastodon et Ekylibre. Pour un service régalien, l'AGPL est généralement compatible avec les politiques de souveraineté numérique (DINUM, ANSSI).

Comment auditer le protocole avant de le retenir ?
Tout est public sur github.com/Pierroons/my-self. Trois portes d'entrée : (1) le whitepaper FR pour la spec cryptographique complète et le modèle de menaces formel ; (2) le code de la démo (PHP 8 + SQLite, ~2000 lignes) pour la vérification d'implémentation ; (3) la page comparatif qui liste 8 catégories d'adversaires couvertes. La démo se relance en local en 30 secondes (git clone + ./run.sh).
Quel coût d'intégration pour notre stack actuelle ?
Deux paliers d'adoption :

Mode Lite — le plus rapide. Vous gardez votre infrastructure email actuelle (lien reset SMTP). Vous ajoutez côté navigateur un champ « mot mémorisé » dont la dérivée HMAC remonte au serveur en plus du token reset. Implémentation typique : 0,5 à 2 jours-développeur pour intégrer dans une stack PHP/Symfony ou Django existante. Aucun changement de schéma de base hors une colonne supplémentaire.

Mode Full — plus structurant. Suppression complète du canal email. Implémentation typique : 3 à 7 jours-développeur selon la complexité du flow d'inscription/recovery existant. Le whitepaper détaille les étapes obligatoires.
Y a-t-il des dépendances externes obligatoires ?
Non. La démo de référence tourne sur PHP CLI 8.0+ avec extension pdo_sqlite. Zéro service tiers, zéro API SaaS, zéro télémétrie, zéro appel sortant. Auto-hébergement complet sur Raspberry Pi (instance de référence chez l'auteur). Les bibliothèques utilisées sont natives au runtime (hash_hmac, password_hash) ou des standards JS du navigateur (crypto.subtle.deriveKey).
Comment la sécurité est-elle vérifiée ?
Trois niveaux : (1) spec formelle dans le whitepaper avec primitives nommées (HMAC-SHA256 par domaine, bcrypt, Argon2id selon le contexte) ; (2) threat model qui liste 8 catégories d'adversaires et la mesure prévue contre chacun (insider, fuite de base, MITM, vol de poste, phishing, force brute, replay, side-channel) ; (3) démo interactive où chaque scénario d'attaque est testable en direct sur la démo Duo Sybil. Aucun audit tiers payant n'a encore été fait — c'est précisément l'un des chantiers que les institutions peuvent contribuer à lancer (audit communautaire ouvert, soumission CNIL/ANSSI pour avis informel).
Que se passe-t-il si l'auteur disparaît ?
Code public sous AGPL : n'importe quel acteur peut forker et continuer. La preuve d'antériorité du protocole est fixée par le tag GitHub v0.1.1 daté du 5 mai 2026 16:01 UTC. Le repository est répliqué sur l'instance auto-hébergée de l'auteur (DEVSERVER) en plus de GitHub. Pour les services régaliens, c'est précisément la garantie qu'un protocole open-source apporte par rapport à un SaaS propriétaire : pas de single point of failure éditorial.
Quelles données sont stockées côté serveur ?
Aucun secret en clair, jamais. Le mot mémorisé / la passphrase ne quittent pas le navigateur. Le serveur ne stocke que la dérivée hashée (bcrypt(HMAC(secret, host))). En mode Full, pas d'email du tout. En mode Lite, l'email est conservé pour le canal de reset, mais devient insuffisant à lui seul pour compromettre un compte. Aucune télémétrie utilisateur, aucune analytics tierce, aucun cookie hors session standard.
Quelles certifications / référentiels couverts ?
Le protocole ne porte pas en soi de certification (c'est l'implémentation côté opérateur qui en porterait, ex. ANSSI CSPN ou critères communs). Il est compatible avec les exigences ANSSI sur les mots de passe (recommandations 2021) et le RGPD (minimisation : moins de données stockées que dans un flux email-reset classique). Pour un déploiement régalien, l'opérateur reste responsable de l'audit final et de la conformité.
